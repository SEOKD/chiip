# ADR-013 — Chiip 하네스 설계

상태: 설계 제안, 단계별 마스터 승인 대기 · 2026-10-31 · 조사 회차 1건(Chiip Laboratory 수동)

하네스(harness)는 모델을 둘러싼 나머지 전부다. 지시문, 도구, 상태 저장, 검증, 권한이 여기에 든다.

## 결정
모델이 자기 구조를 스스로 고치는 자동 진화는 들여오지 않는다. 대신 **기록 → 시험 → 변경 관문 → 사람 승인** 순서로 하네스를 고친다. 첫 작업은 새 규칙이 아니라 실행 기록과 고정 시험셋이다. 둘이 없으면 어떤 변경이 효과가 있었는지 가릴 수 없다.

```text
결정론 문턱 → 모델 회차 → 코드 관문 → 발송
                  ↓
              실행 장부(회차·지시문 버전·입력·산출물·관문 결과)
                  ↓
마스터 교정·실패 → 고정 시험셋(개발용 / 봉인)
                  ↓
제안서 → 변경 관문(잡음·복잡도·누출·봉인 시험) → 마스터 승인 → 반영
                  ↑
평가기는 고도화 대상 바깥(해시 잠금, 마스터 라벨로 보정)
```

## 설계 — 부품 7개
**H1 실행 장부.** 모델 회차, 발송, 발행마다 `knowledge/models/lab/agent/runs.jsonl`에 한 줄을 추가한다. 항목은 기능, 시각, git 커밋, 지시문 해시, 입력 id, 산출물 경로, 관문 결과, 모델 여부다. 기존 기록을 지우거나 고치지 않는다. 비용은 받을 수 없으면 '미확인'으로 둔다.

**H2 결정론 문턱.** `radar/pulse.py`를 모델 바깥의 Windows 작업으로 돌리고 새 자료가 있을 때만 모델 회차를 연다. 포트폴리오, 텐배거, 노션 감시도 같은 방식으로 본다. 빈 회차 약 80%를 없애는 것이 목표다. 실제 절감액은 구현 전까지 미확인이고, 헤드리스 실행 문법은 공식 문서로 확인한 뒤 짓는다.

**H3 고정 시험셋.** 마스터 교정과 실제 실패로 20~50건을 만든다. 각 건은 입력 자료를 함께 저장해 웹 상태가 바뀌어도 재현되게 한다. 개발용과 봉인용으로 나누고 유형을 섞는다(수치 대조, 금지 연결, 출처, 양식, 면책). 주석 기준은 마스터 확인분만 쓴다.

**H4 평가기 보호와 보정.** 평가기 파일 해시를 `evals/verifier.lock`에 고정하고, 달라지면 테스트가 실패한다. 이 잠금은 변조를 드러낼 뿐 막지는 않는다. Proviser는 항목별 불합격선을 두고(하나라도 미달이면 불합격), 마스터 라벨과의 차이를 매달 잰다. 라벨이 12건 쌓이기 전에는 편향을 단정하지 않는다.

**H5 변경 관문.** 제안서는 파일 단위로 쓰고 예측과 깨질 위험을 적는다. 한 번에 하나만 바꾼다. 통과 조건은 다섯 가지다.
1. 본 표본과 떼어 둔 표본 모두 잡음 폭을 넘는 악화가 없다(`--gate`, 이번에 잡음 폭과 최소 표본 12건 반영).
2. 같은 비용의 단순 기준선보다 낫다. 기준선 = 지시문을 고치지 않고 코드 관문이나 재시도만 쓰는 방법.
3. 복잡도 예산: 지시문 글자 수가 늘면 그만한 개선을 보여야 한다.
4. 누출 검사: 일반 규칙에 특정 종목, 회사, 숫자가 박히면 거부한다. 마스터 지시 원문은 예외.
5. 봉인 시험 통과. 그 뒤 마스터 승인.

**H6 통제 장부.** 규칙, 훅, 관문마다 발생 사고, 측정 지표, 만료 조건을 적는다. 14일간 해당 위반이 없으면 삭제 후보로 올린다(AAP-20261031-03 포함). 마스터 상시 원칙은 만료 대상이 아니다. 분기마다, 그리고 모델 변경 때 부품을 하나씩 빼는 시험을 한다. 예약 일정과 문서가 어긋나면 표류로 잡는다.

**H7 권한 경계.** 권한 설정은 마스터 결정이다. 제안: 예약 작업에서 `D:\local-only` 읽기를 거부 규칙으로 막고, `field-intake`·`ib-digest`처럼 로컬이 필요한 작업은 마스터 세션에서만 돌린다. 비밀 키는 발송 스크립트만 읽게 한다. 셸 경유 우회까지 막지는 못하므로 완전한 격리가 아니다.

## 들여오지 않는 것
| 기법 | 이유 |
|---|---|
| 모델이 지시문을 직접 고치는 자동 진화 | 떼어 둔 시험 이득이 0인 사례가 있다. 치입의 정답은 늦게 나오고 판단이 섞여 외부 기준이 약하다 |
| 실행 중 자기 수정(PILOT) | 읽은 범위에서 떼어 둔 구간을 찾지 못했고 같은 과제를 반복 평가한다 |
| 다중 역할 팀 확대 | 효과 근거가 엇갈린다. 이미 생성과 평가가 나뉘어 있다 |
| 무인 소프트웨어 공장식 운영 | 성공을 입증한 공개 데이터가 없다. 치입에는 공개 채널 자동 게시 금지 원칙도 있다 |

## 단계와 판정
| 단계 | 내용 | 승인 필요 | 판정 |
|---|---|---|---|
| 1 | H1 실행 장부, H4 평가기 잠금, 표류 수정 | 설계 승인 | 7일 뒤 산출물의 95% 이상이 커밋·지시문 해시와 연결 |
| 2 | H2 결정론 문턱 | 예약 방식 변경 | 14일간 빈 모델 회차 90% 감소, 놓친 알림 0건 |
| 3 | H3 시험셋 20건, H5 관문 | 마스터가 정답 확인 | 첫 변경 1건을 전 과정으로 판정 |
| 4 | H6 통제 장부, 제거 시험 | 삭제는 건별 | 활성 지시 47건 → 35건 이하, `--gate` 악화 없음 |
| 5 | H7 권한 경계 | 마스터 결정 | 로컬 작업 실패 0건 |

기각 조건: 단계 1 장부가 30일간 어떤 변경 판단에도 쓰이지 않으면 항목을 줄인다. 시험셋 유지가 산출물보다 많은 시간을 먹으면 3단계를 코드 평가만으로 줄인다.

## 위험
- 측정이 형식에 치우쳐 판단 품질을 놓칠 수 있다. 예측 성적표와 마스터 라벨을 함께 본다.
- 평가 기준을 맞추려는 왜곡이 생길 수 있다. 평가기 잠금과 봉인 시험으로 줄이되 없애지는 못한다.
- 결정론 문턱이 끊기면 펄스도 멈춘다. 모델 없이 장애를 알리는 건강 점검을 함께 둔다.
