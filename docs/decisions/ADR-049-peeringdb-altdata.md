# ADR-049 PeeringDB 대체 데이터 — 기각 철회·표적 수집기

- 날짜: 2026-11-20
- 상태: 채택
- 마스터 결정: 2026-11-20 "넣어라" (2026-11-19 Proviser 데이터 채널 탐색이 '기각'으로 적었던 것을 되돌린다)

## 근거

2026-11-20 주 세션이 PeeringDB AUP와 공식 문서를 읽고 다음을 확인했다.

- AUP는 허용 목적으로 '인터넷 연구·분석(Internet research and analysis)'을 든다.
- 전체 데이터베이스 내려받기와 대량 재배포는 PeeringDB 승인이 필요하다.
- 마케팅 명단·광고 표적화·상업 응용은 금지된다.
- 익명 API는 허용된다. 인증을 빼고 부르면 된다.
- 읽은 문서에는 호출 한도 수치가 없다. 2026-11-20 첫 시험에서 짧은 간격으로 연달아 부르자 429(요청 과다)가 났다.

Chiip은 마스터 개인 리서치 에이전트이고 상업적으로 쓰지 않는다. 그래서 아래 조건을 지키는 표적 질의는 AUP의 연구·분석 목적 안에 든다고 본다. 법률 판단이 아니라 이용 조건 해석이며, 애매해지면 마스터에게 묻는다.

## 조건(코드로 지킨다)

- 표적 질의만 한다. 전체 복제·동기화 도구·`since=` 전체 동기화는 쓰지 않는다.
- 익명 GET을 쓰고 `common.contact_ua()`로 우리를 밝힌다.
- 호출 간격은 6초, 회차당 요청은 8건 이하(지금 6건), 수집은 하루 1회다.
- 429나 오류가 나면 그 회차는 아무것도 쓰지 않고 멈춘다(fail-closed). 결과는 pipeline_health에 남긴다.
- 숫자만 저장한다(개수·용량·새 접속 시설과 IX의 ID·날짜). 연락처·사람 이름은 받지도 저장하지도 않는다.
- 원표는 공개 채널(딘스티커 등)에 올리지 않는다. 쓰는 곳은 개인 텔레그램 Pulse, 데이터 허브, Analysis 근거뿐이다.

## 구성

- 설정 `config/peeringdb.yaml`: 시설 7곳, 네트워크 9곳, IX 3곳과 각각 고른 이유.
- 수집기 `radar/pollers/peeringdb.py`(`run_hourly` 1440분 주기, `src-peeringdb`). 저장 위치는 `knowledge/models/peeringdb/`의 `facilities.csv`·`ixs.csv`·`net_presence.json`·`changes.json`.
- 데이터 허브: `gather.py --market`의 `peeringdb` 원천(`--show`).
- Pulse '데이터센터 접속': 의미 있는 변화일 때만 올린다. 대상은 하이퍼스케일러·AI 클라우드의 새 시설·IX 접속과 시설 입주 네트워크 5% 이상 증가다. 첫 회차는 기준선으로만 쓴다.
- 해석 경계: 접속 등록은 용량·매출이 아니다(금지표 '투자 발표 → 공급 증가'와 같은 결의 검증이 필요하다). 등록은 운영자가 스스로 하는 것이라 빠짐이 있다(예: Lambda Cloud는 등록된 시설이 없다).
