## 0. 너(Claude Code)의 역할과 작업 방식

너는 이 저장소 안에 **반도체·AI 하드웨어 산업 리서치 시스템**을 설계하고 구축하는 엔지니어다. 최종 결과물은 하나의 프로그램이 아니라 다음의 조합이다.

- 평문 파일로 된 **지식 레이어** (축적되는 자산)
- 뉴스·공시·논문·보고서를 빠르게 포착하는 **실시간 정보 레이더** (속도)
- 국내 기업이 말하기 전에 상대방·정부·공급망·커뮤니티의 흔적을 찾는 **역방향 레이더** (선행성)
- 채용·인사·조직개편으로 기업의 다음 행동을 읽는 **인재·조직 레이더** (의도)
- 연방·주·시 정부 공개 문서로 규칙과 투자 실행을 먼저 읽는 **미국 정부 감시 엔진** (정책)
- 그 정보를 해석하는 **스킬·서브에이전트·훅** (분석 엔진)
- 변경을 검토·기록하는 **GitHub 워크플로** (데스크)

### 0.2 반드시 지킬 작업 규칙

1. **계획 먼저, 실행은 승인 후.** 각 단계(§18)를 시작할 때 무엇을 만들지 목록으로 보여주고, 사용자가 "승인"이라고 하기 전에는 파일을 만들지 않는다.
2. **승인 게이트에서 멈춘다.** §18의 `🛑 게이트`에서 반드시 작업을 멈추고 결과를 요약한 뒤 다음 지시를 기다린다.
3. **초보자용 보고.** 각 단계가 끝나면 ① 무엇을 만들었는지 ② 사용자가 확인할 파일 ③ 다음 단계를 각각 한두 문장으로 보고한다. 전문 용어는 처음 나올 때 한 줄로 풀어 쓴다.
4. **최신 공식 문서 확인.** 스킬·서브에이전트·훅·헤드리스 실행(`claude -p`)·루틴·GitHub Actions의 정확한 문법과 제약은 기억에 의존하지 말고 code.claude.com 공식 문서를 조회한 뒤 작성한다. 외부 API(DART, 네이버, SEC EDGAR, 텔레그램, 미국 관보·의견서·의회·노동부 데이터, 지방정부 회의 플랫폼 등)도 구현 직전에 공식 문서로 엔드포인트·호출 제한·약관을 확인한다. 문서와 이 지시서가 충돌하면 문서를 따르고 사용자에게 알린다.
5. **작게 커밋.** 의미 있는 작업 단위마다 한국어 커밋 메시지로 커밋한다. 커밋 전 §3 경계 위반이 없는지 확인한다.
6. **불필요한 설치 금지.** 파이썬 표준 라이브러리 + 꼭 필요한 패키지(`pyyaml`, `requests`, `feedparser` 등)로 시작한다. 새 패키지는 이유를 설명하고 승인받는다.
7. **모호하면 묻는다.** 사용자의 리서치 판단 기준, 관심 기업 범위, 알림 기준은 추측해서 확정하지 않는다.
8. **이 지시서도 수정 대상이다.** 더 나은 설계를 발견하면 제안하되, 승인 없이 고치지 않는다.

## 1. 시스템의 목적

### 1.1 핵심 질문

> 무엇이 산업을 제약하는가 → 어떤 기술과 기업이 그 제약을 푸는가 → 부가가치와 이익이 어디로 이동하는가 → 지금 나온 정보가 그 그림의 어느 고리를 바꾸는가 → (투자 모드) 그 변화가 현재 가격에 얼마나 반영됐는가

### 1.2 시스템 중심 문장 (CLAUDE.md 최상단)

> 최종 수요와 시스템 구조에서 병목을 찾고, 해결 기술의 작동 원리·대안·양산성·고객 채택·경제성을 검증한다. 기업별 역할과 실제 공급 관계를 구분하고, 기술 변화가 경쟁력과 부가가치를 어디로 이동시키는지 설명한다. 새 정보는 가장 먼저 포착하되, 그것이 기존 판단의 어느 고리를 바꾸는지로 가치를 매긴다. 출처·시간·단위·제품 세대가 다른 주장을 임의로 합치지 않는다. 결론은 증거가 지지하는 범위에서 내리며, 반증 조건과 다음 확인 사건을 제시한다.

### 1.3 자산의 정의

장기적으로 가치가 쌓이는 것은 **에이전트가 아니라 지식 레이어와 판단 이력**이다.

- 모든 지식은 **마크다운·YAML·CSV·JSON 평문 파일**로 저장한다. 특정 벤더 전용 형식에 가두지 않는다.
- 모든 변경은 git으로 기록한다. 판단 이력 = 커밋·PR 이력.

### 1.4 하나의 시스템, 여러 출력 모드

반도체 리서치와 투자(텐배거) 분석은 **같은 지식 레이어를 공유**한다. 차이는 출력 모드와 일부 스킬뿐이다(§16).

### 1.5 엣지의 정의 — CLAUDE.md에 반드시 명시

이 시스템의 경쟁 우위는 세 원천에서 나온다. 우선순위 순서다.

1. **필드 인텔 (사용자의 직접 취재 정보)** — 이 시스템의 **가장 중요한 차별 원천**이다. 사용자는 전자산업 출입 기자로서 팹 기획·패키지·테스트·장비사 인력과의 네트워크, 학회 현장, 기업 취재를 통해 공개 자료보다 앞선 신호를 얻는다. 다른 리서치 기관과 AI는 이 정보를 가질 수 없다. 시스템은 필드 인텔을 최우선 가중치의 선행 신호로 다루고, 공개 정보가 나올 때마다 필드 인텔과 대조한다. 단, §3의 등급·엠바고·봉인 경계를 반드시 지킨다.
2. **속도와 선행성 (실시간 레이더 + 역방향 레이더 + 인재·조직 레이더 + 미국 정부 감시 엔진)** — 국내 반도체·AI 하드웨어 밸류체인 핵심 기업(§10.2 T0)의 공시·보도자료·뉴스를 시장보다 먼저 포착하고(§10), 더 나아가 **그 기업들이 스스로 발표하기 전에 거래 상대방·정부 서류·무역 거울 데이터·특허·채용·기술 아티팩트·해외 커뮤니티·외국어 언론에 남는 흔적을 찾는다(§11).** 채용 공고와 인사로 기업의 다음 행동을 읽고(§12), 미국 연방·주·시 정부 문서로 규칙 변화와 해외 거점의 실행 단계를 먼저 읽는다(§13). 그리고 기업 비즈니스와 주가에 미치는 영향을 즉시 판정한다.
3. **해석 (엔지니어 관점 + 한국어 1차 자료)** — 양산 엔지니어 출신의 공정·장비·수율 판단력과, 해외 애널리스트가 놓치기 쉬운 한국어 1차 자료(공시·통관 통계·인허가·국내 보도)를 구조화된 지식으로 바꾸는 능력.

속도만으로는 엣지가 아니다. **"먼저 알고(필드 인텔·레이더·역방향 레이더) → 정확히 해석하고(지식 레이어) → 시장 기대와 비교해 차이를 찾는(consensus-gap)"** 세 단계가 연결될 때 엣지가 된다.

세 원천은 서로를 강화한다. 역방향 레이더가 약한 신호의 수렴을 찾으면, 사용자는 그것을 **무엇을 확인 취재할지 알려주는 지도**로 쓴다. 필드 인텔이 확인하면 삼각측량이 완성된다. 반대로 필드 인텔로 먼저 안 사안은 역방향 레이더의 페어북에 등록해, 공개 흔적이 나타나는 순간을 잡는다.

| P19 | **수렴은 사실이 아니다.** 삼각측량 경보도 1차 출처 확인 전에는 "정황"으로 표현한다 | §11.6 |
| P20 | **사람은 임원·공개 직책자의 공개 직업 정보만 추적한다.** 일반 직원은 개인 단위로 추적하지 않고 집계로만 다룬다 | §12.7 |

## 3. 로컬 전용 영역·필드 인텔·컴플라이언스 — 최우선

### 3.1 로컬 전용 폴더 (저장소 바깥)

저장소에 절대 올라가지 않는 정보는 저장소 **바깥** `D:\local-only\`(경로는 0단계에서 확인)에 둔다.

```
D:\local-only\
├── sealed\        # 봉인: 취재원 보호·비보도 정보 (필드 인텔 F3·F4)
│   ├── field\     # 취재 메모 원문
│   ├── capa_overlay.csv
│   └── denylist.txt   # 취재원 이름 등 금칙어 (사용자 직접 작성)
├── embargo\       # 엠바고 자료 (F2) — 해제 시각 전까지
├── licensed\      # 라이선스 자료 원문: IB 리포트 PDF, 유료 구독 자료
└── secrets\.env   # API 키·봇 토큰 (DART, 네이버, 텔레그램 등)
```

규칙:
1. 저장소 어떤 파일에도 취재원 이름·소속 부서·연락처·직접 인용, API 키·토큰을 쓰지 않는다.
2. 저장소에는 로컬 전용 정보를 **추상화 포인터로만** 남긴다: `source_class: A-fab-planning`, `reliability: B2`, `corroboration: pending` — 수치·원문 없이.
3. 봉인 정보 기반 수치(예: 팹 페이즈 캐파)는 `capa_overlay.csv`에만. 저장소 캐파 모델은 공개 자료·자체 추정치만.
4. 클라우드 루틴·GitHub Actions는 구조상 로컬 전용 영역에 접근할 수 없다. 로컬 전용 정보를 쓰는 분석은 **로컬 세션에서만** 수행한다.
5. `denylist.txt` 내용은 출력·인용·커밋하지 않는다. pre-commit 훅은 검사에만 사용한다.
6. `licensed\` 원문(IB 리포트 등)은 저장소에 복제하지 않는다. 저장소에는 메타데이터 + 사용자 소유 요약(자기 말로 쓴 요지·추정치 변경 숫자)만.

### 3.2 필드 인텔 (사용자 직접 취재 정보) 체계

사용자는 앞으로 직접 취재한 정보를 에이전트에 입력한다. 이것이 이 시스템의 핵심 엣지다(§1.5). 입력은 `field-intake` 스킬로 받는다(§7).

**공개 등급 (disclosure class)**

| 등급 | 의미 | 저장 위치 | 사용 가능 모드 |
|---|---|---|---|
| F1 공개 | 사용자 기사로 보도 완료 또는 회사 공식 공개 | 저장소 `sources/` (doc_type: 사용자보도) | 전 모드 |
| F2 엠바고 | 보도자료·발표 자료, 해제 시각 지정 | `local-only\embargo\` → 해제 시 자동 F1 전환 | 해제 전: 기사 준비만 |
| F3 보도 예정 | 취재 완료, 기사화 전 | `local-only\sealed\field\` | 기사 모드(로컬)만 |
| F4 봉인 | 비보도 조건·취재원 보호 대상·배경 설명 | `local-only\sealed\field\` | 기사 모드(로컬)의 맥락 참고만, 인용 불가 |

**신뢰도 평가 — 정보기관식 2축 평가(Admiralty 방식) 채택**

- 출처 신뢰도: A(완전히 신뢰) ~ E(신뢰 불가), F(판단 불가) — 해당 취재원의 과거 적중 이력으로 갱신
- 정보 신뢰도: 1(다른 출처로 확인) ~ 5(의심), 6(판단 불가)
- 예: `B2` = 대체로 신뢰할 만한 출처, 다른 정황과 부합

**선행성 추적 — 엣지의 정량화**

필드 인텔 항목이 이후 공개 자료(공시·회사 발표·타 매체 보도)로 확인되면 `publicly_confirmed_at`과 확인 출처를 기록한다. `score_field_intel.py`가 다음을 집계한다.
- 선행 일수(취재 시점 → 공개 확인 시점)
- 적중률(확인/부정/미확인)
- 취재원 등급별 정확도 → 출처 신뢰도 자동 갱신 제안

이 집계는 사용자의 엣지를 숫자로 증명하는 트랙레코드다. 단, 집계 결과 파일도 취재원 식별 정보 없이 `source_class` 단위로만 저장소에 남긴다.

**레이더와의 대조**

로컬 실행 시 레이더가 새 정보를 포착하면 필드 인텔과 대조해 다음을 표시한다: `취재로 이미 파악` / `취재 정보와 상충` / `취재 정보를 공개 확인` / `무관`. 클라우드 실행에서는 이 대조를 하지 않는다.

### 3.3 컴플라이언스 경계

사용자는 기자로서 비공개 정보를 접한다. 취재원 보호, 자본시장법상 미공개중요정보 이용·시장질서 교란행위 리스크, 언론사 윤리강령 때문에 다음을 구조적으로 강제한다.

1. **투자 모드(invest)와 공개 콘텐츠 모드(public)는 `local-only\` 를 읽지 않는다.** 공개 자료로 확인된 주장(`public_corroborated: true`)과 F1 필드 인텔만 사용한다.
2. F3 항목은 사용자 기사가 보도된 시점(F1 전환) 이후에만 투자·공개 모드에서 사용할 수 있다. 전환 시각을 기록한다.
3. 엠바고 자료는 해제 시각 전에 어떤 알림·요약·출력에도 내용을 담지 않는다("엠바고 자료 1건 대기, 해제 시각 ○○" 수준만).
4. 사용자가 기사 모드·로컬 전용 정보를 투자 모드로 옮기려 하면 경고를 출력한다.
5. 너는 법률 판단을 하지 않는다. 투자 모드 출력 하단에 "공개 자료 기반 분석이며 투자 권유가 아님" 문구를 넣는다.
6. 웹 수집은 사이트 이용약관과 robots.txt를 준수하고, 로그인·유료벽을 우회하지 않는다. 뉴스·리포트 원문 전체를 저장소에 복제하지 않는다(메타데이터 + 자기 말 요약 + 링크).
7. **역방향 레이더의 공개 정보 원칙.** 역방향 레이더는 누구나 정당하게 접근할 수 있는 공개 자료(공시·정부 문서·통계·특허·공개 웹·공개 커뮤니티)만 다룬다. 공개 자료를 조합해 얻은 추론은 정당한 리서치이지만, 직원 익명 커뮤니티 등에서 **내부자 유출로 보이는 정보**(`insider_like: true`)는 미공개중요정보일 위험이 있으므로 투자·공개 모드에서 사용하지 않는다. 판단이 애매하면 사용자에게 묻는다.

## 7. 스킬 명세

### 7.1 기반 스킬

| 스킬 | 목적 | 완료 기준 |
|---|---|---|

## 10. 실시간 정보 레이더 (Radar)

### 10.1 목적

세미애널리시스와 월가 리서치 하우스의 경쟁력은 리서치 깊이만이 아니라 **뉴스를 가장 먼저 접하고, 그것이 기업 비즈니스와 증권시장에 미치는 영향을 즉시 엣지 있게 판정하는 능력**에 있다. 레이더는 다음을 수행한다.

1. 학회 논문, 밸류체인 기업의 기술 자료·보도자료·공시, IB·증권사 리서치, 뉴스, 산업 지표를 상시 수집
2. **국내 반도체·AI 하드웨어 밸류체인 핵심 기업(T0)을 최우선·최고빈도로 감시**
3. 새 정보를 지식 레이어·필드 인텔과 대조해 novelty와 영향 판정

### 10.4 수집 엔진 설계 원칙

1. **수집은 결정론적 스크립트, 판단만 모델.** `radar/pollers/*.py`는 모델을 호출하지 않는다. RSS·API·검색 API로 새 항목을 가져와 정규화(§5.12)하고 해시로 중복을 제거한다. **새 항목이 있을 때만** `run_triage.py`가 모델을 호출한다. 수 분 간격 폴링을 모델로 직접 하면 사용량 한도를 소진하므로 금지한다.
2. **폴링 빈도는 티어 × 시간대로 조정한다.** 초기안(사용자 확정):

   | 구간 (KST) | T0 국내 공시·뉴스 | T2 글로벌 |
   |---|---|---|
   | 장중 08:00~16:00 (공시 집중 시간대 포함) | 3~5분 | 1시간(클라우드) |
   | 저녁 16:00~23:00 | 10분 | 1시간 |
   | 미국 장·실적 시간대 (대략 22:00~07:00) | 30분 | 30분~1시간 (주요 실적일엔 로컬로 상향) |
   | 주말 | 1시간 | 3시간 |

   `calendar.csv`에 실적·학회·제품행사가 있는 날은 해당 기업·원천 빈도를 자동 상향한다.
3. **로컬 실행 방식은 구축 시 비교 후 결정한다.** 후보: ① Windows 작업 스케줄러가 `run_poll.py` 실행 → 신규 항목 시 헤드리스 Claude Code 호출 ② 데스크톱 앱 로컬 예약 작업. 각 방식의 최소 간격·앱 상시 실행 필요 여부·구독 인증 동작을 공식 문서로 확인해 사용자에게 장단점을 제시하고 선택받는다.
4. **이벤트 클러스터링.** 같은 사건을 다룬 여러 원천은 하나의 `event_cluster`로 묶는다. 클러스터에는 **최초 보도 원천과 시각**을 기록한다(사용자 소속 매체의 선행 보도 여부도 집계 가능).
5. **1차 출처 우선.** 뉴스로 먼저 포착해도 공시·회사 발표가 나오면 카드를 갱신하고 `primary_source_confirmed`를 바꾼다.
6. **실패를 숨기지 않는다.** 원천 접근 실패·호출 제한·형식 변경은 `radar/state/health.json`에 기록하고 다이제스트에 "수집 장애" 항목으로 표시한다.
7. **비용 상한.** 일일 모델 호출 수·P0 심층 분석 수 상한을 `alert_rules.yaml`에 둔다. 상한 도달 시 저우선 항목은 다이제스트로 이월한다.

### 10.5 처리 파이프라인

```
[폴러] 수집·정규화·중복제거
   ↓ 새 항목만
[radar-triage] 관련성·이벤트 유형·novelty·등급 1차 판정 (소형 모델)
   ↓ P3 → 아카이브 / P2 → 다이제스트 대기 / P0·P1 ↓
[impact-analyst] 영향 카드 완성: 1차 영향 → 2차 전파 → 시장 맥락 → 엣지 해석
   ↓ (로컬 실행 시) 필드 인텔 대조
[notify] 텔레그램 개인 알림 (P0 즉시, P1 묶음)
   ↓ P0
[flash-note] 30분 내 1쪽 메모 → outputs/flash/
   ↓ 사용자 검토
[claim-intake] 확인된 사실만 주장으로 승격 → PR
```

### 10.6 영향 판정 방법

**알림 등급 (`alert_rules.yaml` 초기안, 사용자 확정)**

| 등급 | 조건 예시 | 전달 |
|---|---|---|
| P0 | T0의 잠정실적·실적·가이던스 변경·대형 공급계약·대규모 증설/CAPEX 변경·생산 차질, 업계 판도를 바꾸는 T2 발표(주요 고객의 공급사 변경 등) | 즉시 알림 + 플래시 노트 |
| P1 | T0 관련 신제품·인증·양산 진척, T0 대상 IB 의견·목표가 변경, T2 실적, 핵심 지표 서프라이즈 | 1시간 내 묶음 알림 |
| P2 | T1 공시, 학회 논문, 표준 업데이트, 일반 업계 뉴스 | 아침·저녁 브리프 |
| P3 | 반복 보도, 관련성 낮음 | 아카이브 |

**영향 판정 순서**
1. **1차 출처 확인**: 공시·회사 발표인가, 보도인가, 재인용인가
2. **novelty**: 지식 레이어(claims·theses)와 비교 — 신규/수정/반복
3. **1차 영향**: 어느 기업의 어느 실적 동인(물량·함량·가격·점유율·원가·시점)에 어느 방향·규모·시점으로
4. **2차 영향 전파**: `supply_relations.csv` 경로를 따라 공급사·고객·경쟁사 영향. 경로와 관계 상태를 명시하고, 관계가 `미확인`·`후보`면 신뢰도를 낮춘다
5. **시장 맥락**: 주가 반응(가능한 경우 종목·업종지수 대비), 컨센서스 대비, 이미 반영 여부. 확인 못 하면 "미확인"
6. **엣지 해석**: 시장이 다르게 볼 수 있는 해석을 **가설로 표시**. 근거는 테제·필드 인텔(로컬)·엔지니어 관점
7. **기사 각도**: 야마 후보 1문장

시장 데이터(주가) 원천은 구축 시 후보(공식·비공식 라이브러리, 무료 API)를 비교해 신뢰성·약관을 보고하고 사용자 승인으로 정한다.

### 10.7 알림 채널

- **텔레그램 개인 봇 → 사용자 개인 대화방**으로만 발송. 사용자가 운영하는 공개 채널(딘스티커)에는 절대 자동 게시하지 않는다.
- 봇 토큰은 `local-only\secrets\.env`. 클라우드 루틴의 알림은 PR·다이제스트로 대체하거나, 별도 승인 시 저장소 시크릿 사용.
- 알림 형식(모바일 가독성):
  ```
  [P0] SK하이닉스 | 수주·공급계약 | 15:43 (공시 +2분)
  무엇: ...(1문장)
  영향: HBM 매출 상향·중 / 2027H1 (1차 판정)
  2차: ○○ 상향(낮음)
  시장: 미확인
  야마: ...
  카드: R-20261027-1543-005
  ```
- 사용자가 알림에 답장으로 짧은 피드백(예: "과대", "놓친 맥락: ...")을 남기는 기능은 2차 개선 과제로 둔다.

### 10.8 학회 추적

## 11. 역방향 레이더 (Reverse Radar) — 상대방·정부·커뮤니티 자료 속 국내 기업 흔적 포착 엔진

### 11.0 왜 이 엔진이 필요한가

평범한 리서치 에이전트는 "삼성전자 협력"을 검색한다. 그러면 이미 기사로 나온 정보를 시장과 같은 속도로 읽게 된다. 이 엔진은 반대로 움직인다. **국내 기업이 스스로 말하기 전에, 그 기업의 거래 상대방·정부·공급망·개발자·커뮤니티가 남긴 흔적을 먼저 찾는다.**

협업은 두 회사 사이의 사건이다. 한쪽이 침묵해도 다른 쪽에서 먼저 새어 나온다. 공시 규칙이 다른 나라의 상대방 공시, 공장 인허가 서류, 채용 공고 한 줄, 드라이버 코드 한 줄, 공동 특허, 협력사 시상 보도자료, 해외 커뮤니티 글이 그 통로다.

**설계 명제 (CLAUDE.md에 요약 수록)**

1. **대칭성**: 모든 협업은 상대방 쪽에도 흔적을 남긴다. 국내 기업을 가장 빨리 아는 방법은 국내 기업이 아니라 그 상대방을 보는 것이다.
2. **가장 약한 고리**: 공시 규칙이 가장 엄격하거나 홍보 동기가 가장 강한 쪽이 먼저 말한다(미국 상장사의 공시 의무, 중소 공급사의 수주 홍보, 지방정부의 투자 유치 홍보).
3. **서류가 말보다 먼저다**: 인허가·보조금·특허·상표·통관 서류는 발표보다 먼저 제출된다.
4. **말보다 물건**: 메모리 호환 목록(QVL), GPU BIOS의 메모리 제조사 표기, 통관 실적, 분해 분석은 실제로 출하된 것을 보여준다.
5. **삼각측량**: 강한 신호 하나보다, 서로 독립된 약한 신호 여러 개의 수렴이 더 빠르고 더 단단하다.
6. **언어 차익**: 대만·중국·일본 공급망 쪽 현지어 보도가 영어·한국어 보도보다 먼저 나오는 경우가 많다. 한·영·중·일 4개 언어로 본다.
7. **침묵도 신호다**: 있어야 할 언급이 사라지는 것도 기록한다.
8. **마지막 꼭짓점은 필드 인텔**: 삼각측량의 결정적 확인은 사용자의 현장 취재로 한다(§3.2). 역방향 레이더는 사용자가 **무엇을 물어봐야 하는지**를 알려주는 취재 지도이기도 하다.

### 11.6 M6 시그널 사다리와 삼각측량

**신호 강도**

| 강도 | 정의 | 예시 |
|---|---|---|
| S0 노이즈 | 근거 없는 주장, 재인용 | 출처 없는 SNS 재게시 |
| S1 루머 | 익명 커뮤니티·SNS, 출처 불명 보도 | Reddit 글, 익명 계정 |
| S2 정황 | 간접 흔적 | 채용 문구, 학술 공동 저자, 거울 데이터 변화, QVL 신규 부품번호, 웹 변경, 침묵 신호 |
| S3 준공식 | 공적 서류·1차 취재 보도 | 인허가 서류, 정부 과제 참여, 공동 특허, 상표 출원, 상대방 경영진의 완곡어 발언, 현지 언론 1차 보도 |
| S4 공식(상대방) | 상대방의 공식 실명 언급 | 상대방 공시·보도자료·시상 발표·공급사 명단 |
| S5 확정(양측) | 양측 공식 확인 | 계약 공시, 공동 발표 |

**삼각측량 규칙 (초안, 사용자 확정)**

- **독립성 판정**: 같은 원출처를 재인용한 신호는 하나로 센다(P6). 독립 = 서로 다른 레이어 **그리고** 서로 다른 원출처.
- **수렴 경보**: 같은 페어에 대해 ① 독립 S2 두 개 이상, 또는 ② S1 두 개 이상 + S2 하나 이상 → `수렴 경보` → 영향 카드 P1
- **단독 경보**: S3 하나 → P1 / T0 관련 S4 이상 → P0
- **주장 승격**: S3 이상만 claim-intake 대상(`claim_type: 추정` 또는 `채널체크`), S4 이상은 상대방 측 `확정사실`. S1·S2는 `radar/reverse/signals/`에만 남는다(P14·P16).
- **가중치**: 초기에는 고정값(S1=1, S2=3, S3=8, S4=20, S5=40 × 원천 신뢰도 × 독립성). 선행성 장부(M8)가 쌓이면 레이어·원천별 가중치 조정을 **제안**하고, 사용자 승인 후 반영한다.
- **필드 인텔 연결 (로컬 실행만)**: 수렴 경보가 나면 관련 필드 인텔과 대조하고, 사용자에게 **확인 취재 질문 3개**를 제안한다. 필드 인텔로 확인되면 내부 확신도는 올리되, 저장소와 투자·공개 모드에는 §3 경계에 따라 추상 포인터만 남긴다.

### 11.7 M5 완곡어 해석기

상대방 콜·공시·발표는 실명 대신 익명 표현을 자주 쓴다. 이를 후보 실체로 매핑하되 **해석은 가설**이다(P17).

절차:
1. 익명 표현 포착 (lexicon의 `euphemisms` + 일반 패턴: "Customer A", "a major customer in Asia", "韩系大厂" 등)
2. 후보 나열: 지역·제품·규모 조건을 만족하는 실체
3. **경쟁 가설 분석(ACH)**: 후보별로 일치·불일치 증거 표 작성 — 매출 비중 대비 후보의 구매 규모, 지역 매출 분해, 과거 공시의 실명 노출, 제품 사양·시점, 다른 레이어 신호
4. 출력: "Customer A는 SK하이닉스일 가능성이 높음 (일치 근거 3, 불일치 1, 판단 가정 명시)". 확률을 쓰면 가정임을 표시
5. red-team에 반대 후보 검토를 요청

### 11.8 M7 침묵 탐지기

있어야 할 것이 사라지는 것을 찾는다. 엔티티·페어별로 **기준선(baseline)**을 저장한다.

- 공급사 명단·파트너 페이지에서 삭제
- 매 분기 콜에서 언급되던 고객·제품 언급의 중단
- 정례 학회 발표 불참, 표준 기고 중단
- 특정 직무 채용 공고 일괄 마감
- 인허가 신청 철회·보류, 공시유보 연장

침묵은 S2 정황으로만 취급한다. 반드시 대안 설명(단순 개편·문구 변경)을 함께 적고 확인 질문을 만든다.

### 11.9 커뮤니티·비공식 원천 운용 규칙

1. **단서 전용**: 커뮤니티 신호는 S1. 다른 레이어로 확인되기 전에는 어떤 출력에서도 사실로 표현하지 않는다.
2. **계정 평판 장부** (`knowledge/handle_reputation.csv`): `platform, handle, first_seen, claims, confirmed, refuted, avg_lead_days, notes`. 공개 계정의 공개 게시물 적중 이력만 기록한다. **신원 추적·실명 추정은 하지 않는다.**
3. **내부자 유출 의심 게시물**: "우리 팀에서", "사내에서" 같은 내부자 성격 게시물은 `insider_like: true`로 표시한다. 미공개중요정보일 위험이 있으므로 **투자·공개 모드에서 사용 금지**, 기사 모드에서도 취재 단서로만 쓴다.
4. **금지**: 비공개 그룹·유료 커뮤니티 무단 수집, 위장 계정, 로그인·유료벽 우회, 약관상 자동 수집 금지 플랫폼 수집, 개인 게시물 장문 저장(링크 + 자기 말 요지만).
5. **루머의 운명을 기록**: 루머가 공식 확인되거나 부정되면 선행성 장부와 계정 평판 장부를 함께 갱신한다. 이것이 "어떤 루머 원천이 진짜 선행 지표인가"를 데이터로 알려준다.

### 11.10 사전 신호 플레이북 (Indicators & Warnings)

정보기관의 경보 지표(I&W) 방식을 차용한다. 사건 유형별로 **"이 사건이 일어나기 전에 먼저 나타나는 흔적"**을 정의해 두고 기다린다. 각 페어 파일의 증거 지도는 이 표에서 출발한다.

| 사건 유형 | 선행 흔적 (먼저 나타남) | 확인 흔적 |
|---|---|---|
| 신규 팹·증설 | 환경영향평가·건축 허가, 전력·용수 인프라 신청, 지자체 인센티브 안건, 건설사·장비사 수주 공시, 현지 채용, 대한국 장비 수출 증가 | 착공식, 장비 반입, 가동 발표 |

### 11.13 백테스트와 성과 측정

**구축 직후 백테스트 (4단계)**

**운영 지표 (`score_reverse.py`, 주간·월간)**
- **선포착률**: T0 관련 협업·투자 사건 중, 공식 발표 또는 국내 첫 보도보다 먼저 신호를 잡은 비율
- **평균 선행 일수**: 레이어별·원천별
- **수렴 경보 정밀도**: 경보 중 이후 확인된 비율

### 11.14 이 엔진을 운영하는 태도 (CLAUDE.md 요약 수록)

- 남들이 기사를 검색할 때, 우리는 **서류**를 읽는다.
- 국내 기업을 가장 빨리 아는 길은 **상대방**을 보는 것이다.
- 4개 언어로 본다. 한 언어로 보는 리서치는 반쪽이다.
- **물건**이 말보다 정직하다.
- 무엇이 나타나야 하는지 **미리 적어두고** 기다린다.
- **침묵**도 기록한다.
- 독립된 약한 신호의 **수렴**을 믿되, 수렴이 사실은 아니다. 마지막 확인은 1차 출처와 **필드 인텔**이다.

## 12. 인재·조직 레이더 (Talent & Org Radar) — 채용·인사·조직개편 추적 엔진

### 12.0 왜 독자 엔진이 필요한가

**돈보다 사람이 먼저 움직인다.** 팹이 램프하기 전에 설비·공정 엔지니어 채용이 먼저 늘고, 새 고객을 잡기 전에 해외 고객 대응 인력이 먼저 뽑히며, 전략이 바뀌기 전에 임원 인사와 조직개편이 먼저 발표된다. 채용 공고는 회사가 **앞으로 6~12개월 동안 무엇을 하려는지** 스스로 적어 공개하는 문서이고, 인사는 **경영진이 무엇을 우선순위로 정했는지**를 보여주는 문서다.

일반 뉴스 레이더(§10)는 인사 발표 기사를 잡을 수는 있지만, ① 채용 공고를 매일 스냅숏으로 쌓아 추세를 보는 일 ② 공시 속 임원 명단 변화로 조직도를 재구성하는 일 ③ 미국 노동부 공개 데이터로 해외 거점 인력 증가를 읽는 일은 하지 못한다. 그래서 별도 엔진으로 만든다.

**대상**: 1차로 **삼성전자(DS부문 중심, 해외 반도체 법인 포함)와 SK하이닉스(해외 법인·자회사 포함)**. 안정화 후 T0 나머지 5사로 확장(사용자 승인).

- `function` 분류: 공정 / 설비 / 패키징·테스트 / 설계(회로·SoC·IP) / 소프트웨어·펌웨어 / 품질·신뢰성 / 고객 대응(FAE·AE) / 구매·공급망 / 영업·마케팅 / 건설·인프라·환경안전 / 연구 / 경영지원
- 사업장 사전(`config/talent/sites.yaml`): 국내외 사업장·연구소·해외 법인 소재지의 표기 변형을 정규화
- 기술·장비·고객 키워드는 `config/keywords.yaml`과 `config/lexicon/`을 재사용

### 12.4 채용 신호 해석 틀 (가설 — 백테스트로 검증 후 확정)

| 채용 신호 | 가능한 해석 (가설) | 확인할 것 |
|---|---|---|
| 특정 사업장의 공정·설비 엔지니어 공고 급증 | 신규 라인 램프 또는 전환 투자 | 인허가·장비 반입·거울 무역 데이터(§11.5) |
| 신규 기술 키워드 첫 등장 (예: 새 패키징 방식, 새 메모리 인터페이스) | 개발 착수 또는 양산 준비 | 학회 발표·특허·로드맵 발언 |
| 해외 고객 대응(FAE·AE) 직무 신설·증가 (특정 국가·도시) | 해당 지역 고객 확보·확대 | 상대방 공시·현지 언론(§11) |
| 미국 거점 공정·설비 직무 노동인증 건수 증가 | 미국 공장 램프 단계 진입 | 주 정부·지자체 서류(§13) |
| 건설·인프라·환경안전 직무 증가 | 신규 부지 공사 단계 | 건축 허가·환경 인허가 |
| 같은 공고의 반복 재게시, 장기 미충원 | 인력 확보 난항 → 일정 지연 위험 | 현장 취재 |
| 특정 직무 공고 일괄 마감·채용 중단 | 투자 속도 조절 가능성 (침묵 신호, §11.8) | 경영진 발언·CAPEX 가이던스 |
| 경력 요구 연차 상향, 경쟁사 출신 우대 문구 | 기술 격차 만회 시도 | 인사·외부 영입 |

채용 지표는 **선행 지표 후보**일 뿐이다. 채용 증가를 증설 확정으로 쓰지 않는다(§2.1 금지표).

### 12.5 인사·조직 해석 틀

정기 인사가 발표되면 다음 지표를 **전년·전전년과 같은 표**로 비교한다.

| 지표 | 의미 |
|---|---|
| 직급별 승진자 수 (사장·부사장·상무 등) 와 부문별 분포 (반도체 vs 세트, 메모리 vs 파운드리 vs 패키징) | 회사가 보상하는 사업 |
| 기술·엔지니어 출신 비중, 연구소 출신 비중 | 기술 경쟁력 우선순위 |
| HBM·첨단 패키징·파운드리 고객 대응 관련 보직의 신설·격상 | 전략 키워드 |
| 사업부장·연구소장·해외 법인장 교체 | 실적 책임·전략 전환 |
| 외부 영입 (경쟁사·고객사·해외 출신) | 부족한 역량의 자인 |
| 신설·통합·폐지 조직명 | 가장 직접적인 전략 문서 |
| 세대교체 정도 (보도자료에 공개된 범위의 연령대) | 조직 변화 속도 |

**인사 시즌 운용 모드**: 예년 정기 임원 인사 시기(구축 시 과거 발표일을 1차 출처로 확인해 `calendar.csv`에 등록) 전후 2주 동안:
1. 사전: 비교 프레임(전년 표) 준비. 하마평은 필드 인텔(F3·F4, 로컬)로만 받는다.
2. 발표 직후 **60분 내 `org-flash`** (§7.2.2): 무엇이 바뀌었나 / 비교 표 / 테제 연결(예: HBM 경쟁력, 파운드리 고객 확보) / 기사 각도 / "1차 판정" 표시
3. 후속 조직개편 발표 시 `knowledge/org/` 갱신, 다음 분기보고서 임원 현황으로 재확인

### 12.6 스키마

임원 파일 `knowledge/people/<slug>.md` — **임원 및 공개 직책자의 공개 직업 정보만**:

```markdown
id: pe-<slug>
name: 
company: co-samsung
current_role:            # 직위·보직 (출처 필수)

public_appearances:      # 학회 기조연설·공식 발언 (출처)

```

조직 변경 `knowledge/org/<company>/org_changes.csv`:
```
date,company,change_type,unit,detail_ko,people_ids,source_id,linked_theses
```
`change_type`: 신설|통합|폐지|격상|격하|수장교체|겸직|외부영입|해외법인장교체

```
company,period,segment,employees,avg_tenure_years,avg_pay,source_id
```

채용 집계 `knowledge/models/hiring_index.csv` (일·주 단위 집계, 개별 지원자·직원 정보 없음):
```
date,company,site,function,new_postings,active_postings,closed,reposts,new_keywords
```

### 12.7 개인정보·윤리 경계

1. 추적 대상은 **임원과 공개 직책자**(대표이사, 사업부장, 연구소장, 해외 법인장, 공개 발표한 기술 리더)의 **공개된 직업 정보**뿐이다. 사생활·가족·연락처·사진은 수집하지 않는다.
2. 일반 직원은 **개인 단위로 추적하지 않는다.** 채용·인력은 집계 수치로만 다룬다.
3. 노동부 공개 데이터는 공개 파일이지만 개인 식별 정보가 포함될 수 있는 필드는 저장하지 않고 **고용주·직무·근무지·임금 수준의 집계만** 남긴다.
4. 인사 하마평·내정 정보는 필드 인텔 F3·F4로 다루며, 공식 발표 전에는 투자·공개 모드에서 쓰지 않는다.
5. 국내 개인정보 보호 법규를 존중한다. 판단이 애매하면 저장하지 않고 사용자에게 묻는다(너는 법률 판단을 하지 않는다).

## 13. 미국 정부 감시 엔진 (US Gov Watch) — 연방·주·시 정부 공개 정보 추적

### 13.0 왜 독자 엔진이 필요한가

반도체·AI 하드웨어 산업의 규칙은 지금 상당 부분 **미국 정부 문서**에서 정해진다. 수출통제, 관세(무역확장법 232조 등), 반도체 보조금·세액공제, 첨단 패키징 지원, 데이터센터 전력, 공장 인허가가 모두 연방·주·시 정부의 공개 문서로 먼저 나온다. 삼성전자(텍사스 오스틴·테일러)와 SK하이닉스(인디애나 웨스트라피엣)는 미국 지방정부의 안건에 직접 등장하는 당사자이기도 하다.

미국 정부 문서는 ① 양이 방대하고 ② 기관마다 형식이 다르며 ③ 상당수가 **공식 발표 전에 미리 공개**된다(관보 사전 공람, 회의 안건 사전 게시, 규정 의견 수렴). 이 시차가 엣지다. 일반 뉴스 레이더로는 잡을 수 없으므로 독자 엔진으로 만든다.

### 13.1 감시 지도 — 거점 레지스트리

`config/us_gov/sites.yaml`: 감시할 거점과 그 거점을 관할하는 모든 정부 단위를 묶는다.

```yaml
- site_id: us-samsung-taylor
  company: co-samsung
  description: 삼성전자 텍사스 테일러 팹
  jurisdictions:            # 구축 시 공식 자료로 확인
    state: TX
    county: Williamson County
    city: Taylor
    school_district: 
    appraisal_district: 
    utilities: []
    state_agencies: [환경청, 감사관실, 주지사실 경제개발, 전력 규제·계통 운영]
  watch_radius_km: 30       # 주변 부지 매입·인프라 안건 감시 반경
- site_id: us-samsung-austin
- site_id: us-skhynix-westlafayette
```

1차 거점: 삼성전자 오스틴·테일러(텍사스), SK하이닉스 웨스트라피엣(인디애나). 2차(사용자 승인): 고객·경쟁사 거점(애리조나·뉴욕·아이다호·오하이오 등의 팹·패키징 공장)과 대형 AI 데이터센터 밀집 지역(버지니아·텍사스·조지아 등).

### 13.2 연방 원천

모든 원천은 구축 시 API 문서·키 발급·호출 제한·이용 조건을 확인한다. API 키는 `local-only\secrets\.env`(로컬) 또는 승인된 저장소 시크릿(클라우드)에 둔다.

### 13.4 시·카운티·지역 원천

**지방정부 문서는 가장 이르고 가장 구체적이다.** 회의 안건은 법에 따라 회의 전에 사전 게시된다(예: 텍사스 공개회의법은 원칙적으로 72시간 전 게시 — 구축 시 주별 규정 확인).

| 원천 | 무엇을 보나 |
|---|---|
| 시의회·카운티 위원회 안건·회의록·영상 | 세금 감면, 인프라(도로·용수·하수) 협약, 부지 용도 변경 |
| 도시계획·용도지역 위원회 | 부지 확장·신규 건물 |
| 건축 허가 포털 | 건물 단위 공사 착수·공사비 |
| 경제개발공사(EDC) 이사회 | 고용·투자 약속, **코드명 프로젝트** |
| 학군 이사회 | 학군 세금 감면 협약 |
| 카운티 감정평가청 공개 자료 | 공개 범위의 부동산 평가액 변화 = 시설 완공·가동 정황 |
| 지역 상하수도·전력 공급자 이사회 | 용수·전력 공급 계약 규모 |
| 지역 공개 데이터 포털 (Socrata·ArcGIS 등) | 허가·토지 소유권·공사 데이터 |
| 지역 언론 | 회의 방청 보도 |

### 13.5 엔진 설계

**① 플랫폼 어댑터 패턴** — 미국 지방정부는 소수의 회의·문서 플랫폼을 공유한다(예: Legistar·Granicus·CivicClerk·BoardDocs·CivicPlus 안건 센터, Socrata·ArcGIS 공개 데이터). 플랫폼별 어댑터 하나로 수십 개 지자체를 커버한다. 공개 API가 있으면 API를, 없으면 공개 페이지·RSS를 쓴다.

```
radar/usgov/
├── adapters/          legistar.py granicus.py civicclerk.py boarddocs.py civicplus.py socrata.py arcgis.py rss_html.py
├── federal/           fedreg.py fedreg_public_inspection.py whitehouse.py bis.py regulations_gov.py congress.py govinfo.py usitc.py usaspending.py trade_stats.py energy.py
├── state/             tx_*.py in_*.py ...
├── docs/              수집 문서 (gitignore, 메타·발췌만 저장소)
└── run_usgov.py
```

**② 문서 파이프라인**

```
[수집] 안건·회의록·규정·허가 문서
   ↓
[추출] PDF 텍스트 추출 (스캔본은 OCR) → 안건 항목 단위로 분할
   ↓
[매칭] lexicon(§11.2) + 거점 키워드 + 정책 키워드 + 코드명 패턴
   ↓
[신호화] 신호 레코드 (§11.12 형식, layer: L2, 출처 관할 표시)
   ↓
[판정] policy-analyst: 정책 단계·영향·T0 노출
   ↓
[알림·플래시] 정책 플래시 → claim-intake (공식 문서는 S3~S4)
```

**③ 코드명 프로젝트 매처** — 미국 경제개발 안건은 실명 대신 "Project ○○" 같은 코드명을 자주 쓴다. 코드명과 함께 공개되는 속성(투자액·고용 수·부지 면적·전력·용수 수요·업종)을 `knowledge/policy/codename_projects.csv`에 쌓고, 완곡어 해석기(§11.7)와 같은 경쟁 가설 분석으로 후보 기업을 매핑한다. 매핑은 가설이며(P17), 실명이 공개되면 선행성 장부에 기록한다.

**④ 사전 공개 시차 활용** — 다음 일정을 `calendar.csv`에 자동 등록한다: 관보 사전 공람 문서, 규정 의견 마감일, 청문회·공청회, 지방 회의 일정(안건 게시 시점 포함), 보조금 신청 마감, 관세·통제 시행일.

**⑤ 규정 영향 매핑** — `config/us_gov/code_map.yaml`: 수출통제 품목 분류(ECCN)·관세 품목 분류(HTS) → 제품(`product` 엔티티) → T0 기업 노출(매출 지역 비중, 미국·중국 생산 거점). 예: 첨단 컴퓨팅·HBM 관련 통제 품목, 메모리·집적회로 관세 품목. **코드와 규정 내용은 구축 시 현행 규정 원문으로 확인**하고 개정 시 갱신한다.

**⑥ 의견서 분석** — Regulations.gov 문서함에 삼성·SK하이닉스·고객사·장비사·업계 협회가 제출한 의견서를 찾아, 각 사의 입장·제시한 사업 데이터·요청 사항을 요약한다. 기업이 정부에 직접 쓴 문서이므로 발언의 무게가 크다.

**⑦ 실행** — 미국 정부 원천은 **클라우드 루틴**에서 실행한다. 주기는 미국 동부 시간 업무 시간에 맞춘다.

| 원천 | 주기 (초안) |
|---|---|
| 관보 사전 공람·정식 게재, 백악관, BIS | 미국 업무 시간 중 1시간 간격 (클라우드 최소 간격 확인) |
| Regulations.gov, Congress.gov, GovInfo | 일 1회 |
| 주 정부 원천 | 일 1회 |
| 지방정부 안건·회의록 | 일 1회 + 회의 일정 전날 상향 |
| 무역 통계·지출 실적 | 공개 주기(월)에 맞춤 |

### 13.6 정책 단계 구분 — 상용화 상태처럼 분리 기록

정책도 단계가 다르면 의미가 다르다. 하나로 뭉치지 않는다.

| 정책 축 | 단계 |
|---|---|
| 입법 | 발의 → 위원회 → 본회의 통과 → 양원 통과 → 서명 → 시행 |
| 행정 규칙 | 조사 개시 → 규칙안 → 의견 수렴 → 최종 규칙 → 시행일 → 유예·예외 |
| 보조금·지원 | 발표 → 예비 합의 → 최종 계약 → 단계별 지급 → 조건 변경·회수 |
| 인허가 | 신청 → 보완 → 공청회 → 승인 → 착공 |
| 지방 인센티브 | 안건 상정 → 의결 → 협약 체결 → 이행 점검 |

### 13.7 정책 영향 카드 확장 필드 (§5.13에 추가)

```yaml
policy:
  jurisdiction: federal           # federal|state:TX|county:Williamson|city:Taylor ...
  agency: 
  instrument: 최종규칙             # 법안|행정명령|포고문|규칙안|최종규칙|고시|허가|보조금|안건|의견서|조사
  stage: 시행일확정                # §13.6 단계
  key_dates: {published: , comment_deadline: , effective: }
  affected_codes: [ECCN·HTS ...]
  t0_exposure:                    # 기업별: 노출 경로·규모 추정·근거
    - entity: co-skhynix
      path: "..."
      magnitude: 중
  korea_angle: "한국 정부·업계 대응 가능성, 국내 기사 각도"
  site_link: us-skhynix-westlafayette   # 거점 관련이면
```

### 13.8 스키마와 지표

- `knowledge/policy/policy_events.csv`: `date,jurisdiction,agency,instrument,stage,title_ko,affected_codes,entities,source_id,card_id`
- `knowledge/policy/codename_projects.csv`: `first_seen,jurisdiction,codename,investment,jobs,acreage,power,water,industry,candidates,status,resolved_entity,resolved_at,source_id`
- 지표: 관보 사전 공람 대비 포착 시차, 지방 안건 게시 → 언론 보도까지의 선행 일수, 코드명 매핑 적중률, 정책 플래시 소요 시간, 놓친 정책 사건(`radar-miss`)

### 13.9 경계

- 공개된 정부 문서만 다룬다. 로그인·유료 서비스·정보공개청구 대행 서비스를 무단 이용하지 않는다(정보공개청구가 필요하면 사용자에게 제안만 한다).
- 각 기관 API의 호출 규칙(예: SEC의 접속 식별 요구, 키 발급 조건)을 지킨다.
- 지방정부 회의록에 나오는 일반 시민·직원의 개인 정보는 저장하지 않는다. 기업·기관·공직자 단위 정보만.

## 14. 월가 리서치 방법론 벤치마크

IB·독립 리서치 하우스(세미애널리시스 포함)의 공개적으로 알려진 작업 방식을 이 시스템에 다음과 같이 대응시킨다. 구축 시 각 항목에 대해 공개 자료로 방법을 재확인하고, 원리 수준에서 차용한다(특정 기관의 유료 산출물을 복제하지 않는다).

| 월가·리서치 하우스 관행 | 핵심 원리 | 이 시스템의 구현 |
|---|---|---|
| 커버리지 유니버스와 개시 보고서 | 감시 대상을 정의하고 기업별 기준선 판단을 먼저 세운다 | watchlist 티어, `initiation` 스킬, 엔티티 파일 |
| 동인 기반 실적 모델 | 사업부별 물량×가격×믹스로 실적을 쌓고 이벤트마다 갱신 | `model-build`, `models/companies/` |
| First Take / Flash Note | 이벤트 직후 수 시간 내 1차 해석 배포, 이후 정식 노트로 보강 | `flash-note` (30분 목표), P13 원칙 |
| 모닝 미팅 노트 | 밤사이 변화와 오늘의 카탈리스트를 장 시작 전 정리 | `morning-brief` 07:00 KST |
| 이벤트 플레이북 (프리뷰 → 리뷰) | 사건 전에 기대치를 적어두고, 사건 후 기대 대비로 평가 | `event-preview` + `calendar.csv` + `earnings-delta` |
| 추정치 변경·컨센서스 추적 | 숫자의 방향과 시장 기대와의 차이가 주가를 움직인다 | `ib-digest`의 추정치 변경 기록, `consensus-gap` |
| Variant perception | "우리는 시장과 무엇을 다르게 보는가"를 명시 | impact card `edge_angle`, 테제 파일 |

| 전문가 네트워크 인터뷰 | 업계 실무자 인터뷰로 정성 정보 확보 | 필드 인텔 인터뷰 템플릿 (§3.3 경계 준수) |
| 대체 데이터 | 통관·월매출·채용·인허가·위성 등으로 공식 실적 전에 추세 포착 | `indicators.csv`, 카테고리 H, 한국 통관 데이터 |
| 학회·경영진 접근(NDR) 노트 | 현장 발언의 미묘한 변화 포착 | `conference-tracker`, 사용자 학회·기업 취재 |
| 티어다운·BOM·TCO 분석 (세미애널리시스 특징) | 시스템을 부품 단위로 분해해 가치 귀속·원가 구조 추정 | `supply-chain-map`, `models/bom/` |
| 데이터센터·팹 단위 추적 (세미애널리시스 특징) | 건물·페이즈 단위로 캐파·전력을 추적해 공급을 추정 | `fab_capacity.csv`, 데이터센터 착공·전력 신호 |

| 프리모템·테제 트래커 | 무엇이 틀리게 만들지 미리 적고 추적 | `falsifier`, 테제 판단 변경 이력, `predictions.csv` |

| 공개정보 조사(OSINT)·경보 지표(I&W) | 인허가·통관·특허·채용 같은 공개 서류를 체계적으로 엮고, 사건 전 나타날 흔적을 미리 정의 | 역방향 레이더 §11, 사전 신호 플레이북 §11.10 |
| 경쟁 가설 분석(ACH) | 하나의 해석에 매몰되지 않도록 후보 가설별 증거를 표로 대조 | 완곡어 해석기 §11.7, red-team |
| 인력 데이터 분석 (채용·인사 대체 데이터) | 채용 공고 추세로 기업의 투자·제품 계획을 공식 발표 전에 읽고, 경영진 교체로 전략 변화를 읽는다 | 인재·조직 레이더 §12 |
| 워싱턴 정책 리서치 (정책 데스크) | 규정·법안·청문회·의견서를 단계별로 추적하고 종목 노출로 번역 | 미국 정부 감시 엔진 §13, `rule-impact`, `docket-comments` |

차용하지 않을 것: 정보 접근의 불공정한 관행(미공개중요정보 수집), 근거 없는 목표가 남발, 유료 리포트 원문 재배포.

## 15. GitHub 연계

### 15.1 브랜치 전략
- `main`: 검증된 지식만. 브랜치 보호(PR 승인 필수). 사용자 본인 로컬 커밋 허용 여부는 0단계 결정.
- `claude/*`: 에이전트·클라우드 루틴 자동 제안
- `exp/*`: 스킬 실험

### 15.2 PR 템플릿 필수 항목
신규·수정·상태변경·폐기 주장 수 / 승격된 레이더 카드 / 테제 영향 / 반증 조건 변경 / validate 결과 / 사용자 확인 필요 사항

### 15.3 이슈 템플릿
`hypothesis`, `fact-check`, `article-idea`, **`radar-miss`**(놓친 뉴스: 무엇을, 어디서 먼저 봤나, 언제), **`pair-idea`**(새 관계 가설: 누구와 누구, 무슨 제품, 왜 그렇게 보나 → `pair-open` 스킬로 페어북 등록), **`gov-source`**(새로 감시할 미국 정부 원천·거점 제안 → `config/us_gov/` 등록)

### 15.4 Actions
- `validate.yml`: PR마다 검증 스크립트. 모델 호출 없음.
- `claude.yml`: `@claude` 응답. 구독 토큰 설정은 사용자가 CLI `/install-github-app`으로 진행하도록 안내만 한다(토큰을 너가 다루지 않는다). 턴 상한·타임아웃 설정.

### 15.5 루틴
- 클라우드: T2 글로벌 스윕, 학회·표준 스캔, 일일 다이제스트 초안, T0 폴백 스윕 → `claude/` 브랜치 PR
- 로컬: T0 고빈도 레이더(§10.4), 아침·저녁 브리프, 필드 인텔 대조
- 루틴 프롬프트는 `docs/routines/`에 버전 관리

| 모드 | 답해야 할 질문 | 금지 |
|---|---|---|
| flash | 방금 무엇이 나왔고 1차적으로 무엇을 바꾸는가 | 미검증 표시 누락, 과장된 확신 |
| brief | 지난 구간에 무엇이 바뀌었고 오늘 무엇을 봐야 하나 | 반복 보도 나열 |
| article | 지금 보도할 새로운 변화가 있고 경제적 의미가 충분한가 | 근거 없는 단정, 취재원 노출 |
| report | 무엇이 바뀌고, 왜 가능하며, 누가 유리해지는가 | 목표주가·매수 의견 |
| invest | 실적·현금흐름 기여도와 현재 가격 반영도 | local-only 정보, 확인 안 된 "시장 오판" |
| public | 공개 가능한 근거로 전달할 통찰 | 비공개 정보, 투자 권유, 엠바고 |
| quick | 번역·한 줄·특정 발언만 | 범위 초과 |

### 16.2 공통 출력 구조 (quick·flash 제외)
결론(2~3문장) → 인과 사슬(claim id, 미확인 표시) → 핵심 근거 표 → 반대 검증 요약 → 반증 조건·다음 확인 사건 → 종료 상태

### 16.3 종료 상태
**판단 가능** / **조건부 판단**(가정 명시) / **핵심 근거 부족**(필요 자료 명시)

### 16.4 점수 규칙
10점 평가 시 논리 타당성 / 사업 경쟁력 / 투자 매력도 / 증거 확신도 / 기사 가치를 분리. 감점 요인과 상향 조건을 붙인다.

## 17. 평가 체계

### 17.1 회귀 사례 (`evals/cases/*.yaml`)
```yaml
id: E-001
category: 정의정확성    # 정의정확성|메커니즘|실행검증|공급망|정량일관성|신규성|반증|전달력|레이더판정
prompt: "..."
failure_pattern: "..."
expected_behavior: "..."
severity: critical
source: docs/methodology
```
1단계에서 방법론 문서의 과거 오류 사례로 **초기 10건 이상**(MRM/스위치 혼동, HBM 베이스다이·코어다이 생산 주체, 공장 vs 라인, '첨단 노드' 임의 특정, 4F²·6F² 논리, GPU-메모리 적층 가능성, 광통신 전기·광 구간, 샘플→양산 둔갑, 협력→매출 둔갑, 재인용 중복 집계). 기술적 정답은 사용자 확인 전까지 비워둔다.

### 17.2 출력 평가 기준
정의 정확성 / 메커니즘 / 실행 검증 / 공급망 / 정량 일관성 / 신규성 / 반증 가능성 / 전달력.
**치명 오류**: 출처 조작, 발언 오귀속, 중대한 단위 오류, 샘플의 양산 둔갑, 봉인·엠바고 노출, 1차 출처 미확인 사실의 확정 표현.

### 17.3 레이더 성능 지표 (`score_radar.py`, 주간)
- **탐지 지연**: 원천 게시 → 탐지 → 알림 (T0 목표: 공시·보도자료 탐지 5분, 알림 15분 — 로컬 가동 시)
- **알림 정밀도**: P0·P1 중 사용자가 타당하다고 본 비율 (알림 피드백 기반)
- **누락**: `radar_misses.csv` — 사용자가 다른 곳에서 먼저 본 사건. 누락마다 원인(원천 없음/키워드 없음/빈도 부족/판정 오류)을 기록하고 등록부·키워드·규칙을 수정
- **영향 판정 사후 점검**: 카드의 방향 판정과 이후 1일·5일 주가 반응·후속 사실 비교. 주가는 노이즈가 크므로 **학습 목표가 아니라 점검 자료**로만 쓴다
- **최초 보도 집계**: 이벤트 클러스터의 최초 원천 통계

### 17.3.1 역방향 레이더 지표 (`score_reverse.py`, 주간·월간)
선포착률, 평균 선행 일수(레이어·원천별), 수렴 경보 정밀도, 놓친 사건 원인, 계정 평판 상·하위 — 상세는 §11.13. 백테스트 결과는 `evals/backtest/`에 보관하고 가중치 조정 근거로만 쓴다.

### 17.3.2 인재·조직 지표 (`score_talent.py`, 월간)
인사 발표 → `org-flash` 소요 시간, 채용 신호의 이후 확인율, 사업장별 채용 지수와 이후 CAPEX·램프 발표의 시차 — 상세는 §12.8.

### 17.3.3 미국 정부 지표 (`score_usgov.py`, 월간)
관보 사전 공람 대비 포착 시차, 지방 안건 게시 → 언론 보도 선행 일수, 코드명 매핑 적중률, 정책 플래시 소요 시간, 놓친 정책 사건 — 상세는 §13.8.

### 17.4 필드 인텔 지표 (`score_field_intel.py`, 월간)
선행 일수, 공개 확인률, 출처 등급별 정확도. 식별정보 없이 집계.

### 17.5 운영
사용자 오류 지적 시: ① 회귀 사례 추가 ② 스킬·규칙 수정 ③ 재실행 — 한 세트로 수행.

## 19. 하지 말 것

- 승인 게이트를 건너뛰고 여러 단계를 진행하지 않는다.
- 방법론 문서 문장을 검증 없이 확정 규칙으로 만들지 않는다.
- 저장소에 봉인·엠바고·라이선스 원문, 취재원 정보, 토큰·비밀번호를 만들거나 저장하지 않는다.
- 사용자의 공개 채널에 자동 게시하지 않는다.
- 모델로 직접 고빈도 폴링하지 않는다(수집은 스크립트, 판단만 모델).
- 로그인·유료벽·접근 제한을 우회하거나 약관에 반하는 수집을 하지 않는다.
- 뉴스·리포트 원문 전체를 저장소에 복제하지 않는다.
- 근거 없는 수치·고객 관계·수율·점유율·주가 반응을 채우지 않는다.
- 1차 출처 미확인 보도를 확정 사실로 표현하지 않는다.

- 원천(`config/source_registry.yaml` G·H절, 10개): 미국 연방 공식 RSS(백악관 뉴스·팩트시트·NIST·에너지부) + 기관 도메인 검색(BIS·상무부·USTR·재무부·의회), 주·지방(거점 주지사실·시·카운티), EU 집행위 RSS + 회원국(독·네·프·Chips JU), 일본(관저 RSS + METI·내각부), 대만(행정원 RSS + 경제부·국과회), 중국(상무부·국무원·공신부·발개위), 협회 RSS(OCP·MLCommons·CXL·UEC·UALink·NVMe·IEEE Spectrum) + 협회·학회 도메인 검색(SEMI·SIA·JEDEC·imec·UCIe·Hot Chips·IEDM·ISSCC·VLSI·ECTC·OFC·SEAJ·TSIA·WSTS). 기존 관보(src-fedreg)·행정명령(src-whitehouse) 유지.
- 접근 원칙: 공식 RSS가 열리면 직접 받는다. 자동 접속을 막는 곳(METI·MOEA·상무부 403, MOFCOM DNS 실패 등)은 우회하지 않고 Google News를 정부 도메인(`site:`)으로 제한한 색인을 쓴다. 잡음 제어는 `include_regex`(주제어)와 `max_age_days: 3`.
- 지방정부: Legistar 안건(오스틴)을 역방향 후보와 함께 레이더 항목으로도 넣어 판정·알림(4시간 주기).
- 판정(radar-triage): 정책은 확정 조치가 T0에 직접 닿으면 P0, 행정명령·법 시행·최종 규칙·보조금 확정·재정 예산·규칙안·거점 지방 안건 의결이면 P1, 발의·연설·의견 수렴은 P2. 학회·협회는 표준·사양·MLPerf·학회 프로그램·협회 통계·T0·T2 세미나 자료가 P1. 단계 분리(발의·규칙안·최종·시행 / 발표·계약·지급)와 원문 언어 보존·번역 병기.

### 21.13 실시간 전환·포커스 종목·노션 아카이브 (2026-10-28 마스터 지시) → ADR-009
- **브리프 중단, 실시간 전달**: 아침·저녁 브리프 예약 작업은 비활성. P0·P1 알림은 묶지 않고 건별 즉시 발송(`run_triage.py`), 알림마다 '⭐ 노션 기록' 버튼(`notify.remember_alert`).
- **뉴스는 7곳만, 1차 자료 중심**: 수집 관문(`radar/pollers/gate.py`, `common.save_new_items`가 호출)이 '기사'를 7개 매체만 저장. 국내 언론 검색(src-gnews-t0-ko) 중단. 7개 매체 × 포커스 종목 도메인 검색(src-news7-focus) 추가. 기업 공시·실적은 SEC EDGAR(src-sec-filings: 8-K 실적·중요 계약, 10-Q·10-K, 6-K·20-F) 추가 — DART는 §21.6 결정대로 제외 유지. **(2026-10-28 개정: CNBC·Seeking Alpha 추가 → 9곳. 두 곳은 robots.txt가 AI 수집기를 차단해 Google News 색인 제목·링크로만.)**
- **포커스 종목 점수**(`config/focus.yaml`, `scripts/focus/score.py`, 스킬 `focus-score`, 예약 작업 chiip-focus-score 매일 06:40): 유니버스 62종목을 관심도·내러티브 매력도·펀더멘털 상하방 룸·멀티플 프리미엄 4요소(각 0~10, 가중 평균)로 점수화. 점수는 '지켜볼 이유의 크기'(상하방 크기)로 해석하며 매수·매도 의견이 아니다. 계산 가능한 요소는 코드(백분위), 데이터 공백·맥락은 모델 판단(이유·근거 필수, 출력에 '판' 표시). **5.0 이상만** 종목 자료 수집. 전일 대비 변화·편입·제외를 텔레그램으로.
- 관문 규칙: 정책·학회·협회는 종목 무관 항상 수집. 종목이 잡힌 항목은 포커스 종목이 있어야 저장. 종목 없는 보도자료·공시는 버림. 관심도 집계는 관문 전에 세어(걸러진 종목도) 재편입 가능. 점수 파일이 없거나 3일 지나면 관문 개방(fail_open).
- **노션**: 비공개 허브 '치입 인텔리전스' 아래 '인텔 아카이브'(⭐ 기록)와 '오피니언·인사이트'(마스터 글, 근거 인텔 연결) DB(`config/notion.yaml`). 버튼은 `radar/telegram_inbox.py`(run_poll 5분)가 받아 대기열 → NOTION_TOKEN 있으면 API로 즉시 기록, 없으면 예약 작업이 노션 커넥터로 기록. 기록한 알림에 답장하면 '마스터 메모'로 추가. §21.9의 'Notion = 공개 인사이트만' 규정을 대체 — 공개 사이트로 옮기는 글만 public 규칙·마스터 직접 게시.
- (보강, 같은 날 마스터 지시 "무조건 시의성") **신선도 관문**: 공개 시각 기준 — 수집은 기사·SNS 36시간·보도자료 48시간·공시·정책·학회 72시간 이내만 저장, 텔레그램은 기사·보도자료 24시간·공시·정책·학회 48시간 이내만 발송(`config/alert_rules.yaml` freshness, `gate.is_fresh`). 계기: Google News 도메인 검색의 `when:1d`가 듣지 않아 10/21·22 기사가 10/28에 발송됨. 점수표 텔레그램은 종목명 + 총점(전일 대비)만.
