# Chiip proviser — 6개 기능 추론 재평가 (마스터 지시 2026-10-29)

> "Chip pulse 등 나머지 6개의 추론을 재평가하는 Chip proviser를 만들어라. proviser는 이들의 추론 방식과 다른 접근 방법으로 사고하며 이들 추론 점수를 평가하고, 10점 만점에 9점 미만일 경우 10점으로 끌어올릴 수 있는 근거를 생성하고 이를 각 기능의 작업지시서에 넣어라." 마스터는 기능을 6개만 남겼다 — 프로바이저는 새 기능을 만들지 않고 6개를 고친다.

## 다른 접근 — 기능은 앞으로, 프로바이저는 거꾸로·바깥에서
6개 기능은 **새 정보 → 이야기 → 결론**(내부 관점·귀납·최신 정보 중심)으로 생각한다. 프로바이저는 같은 결론을 다음 순서로 다시 본다.
1. **역추적**: 결론이 참이려면 반드시 참이어야 하는 전제를 3~5개로 거꾸로 적고, 전제마다 1차 출처를 직접 연다.
2. **외부 관점(기저율)**: 같은 종류의 신호가 과거에 얼마나 자주 그 결론으로 이어졌나(참조 집단). 모르면 '기저율 미확인'.
3. **사전 부검**: "6개월 뒤 이 판단이 틀렸다면 가장 그럴듯한 이유는?" — 산출물이 그 이유를 다뤘는가.
4. **경쟁 가설**: 같은 사실을 설명하는 다른 해석 2개 — 산출물이 그것을 가를 자료를 제시했는가.
5. **숫자 재계산**: 단위·분모·기간·통화를 다시 계산한다. 맞출 수 없으면 '비교 불가'였어야 한다.
6. **결정 가치**: 이 산출물이 마스터의 기사·리서치·포지션 판단을 실제로 바꾸는가. 바꾸지 않으면 감점.

기능마다 그 기능이 **쓰지 않는 렌즈**를 하나 더 쓴다.
| 기능 | 기능의 사고 | 프로바이저의 반대 렌즈 |
|---|---|---|
| pulse | 신규성·원본 우선, 알파는 SemiAnalysis 렌즈(내부 관점) | 데스크의 신호 대 잡음("1년 뒤에도 의미 있나") + 고객·공급사 연결의 반영 지연 기저율(Cohen & Frazzini 2008) + 수익률 왜도 기저율(Bessembinder 2018) |
| reporter | 야마(이야기) 우선 | 반론 취재·데스크 킬 테스트("이 야마를 무너뜨리는 가장 강한 1차 자료는?") |
| ten-bagger | 병목 → 해결 기술 → 작은 공급사(내부 관점) | 기저율(Bessembinder 2018) + 경쟁 무시(Greenwood & Hanson 2015: 높은 수익이 공급 증설을 부른다) + 탈락 후보 기록 |
| Notion Tracker | 마스터 의도 우선 | 반(反)동조 검사(찬성·반대 근거의 대칭) + 단일 출처·재인용(origin_id) 점검 |
| Model Lab | 논문 → 파라미터 | 재현성·출판 편향(McLean & Pontiff 2016: 공개 후 예측력 감쇠, Harvey·Liu·Zhu 2016: t>3.0) + 외적 타당성(표본·시장 차이) |
| Weekly Review | 자기 성적 채점 | 자기 채점 편향 교정(단순 기준선 대비 개선 폭) + 주가 원인 금지표 |

## 채점 (10점 = 축 5개 × 2점, 0.5점 단위) — 산출물 표본마다 매기고 평균
| 축 | 2점 | 1점 | 0점 |
|---|---|---|---|
| A 1차성 | 결론의 핵심 숫자·사실을 1차 출처로 직접 확인·링크 | 일부만 1차, 나머지 보도·내부 카드 | 보도·추정뿐 |
| B 인과 사슬 | 고리마다 확정/미확인 표시, 금지표 해당 고리 검증 | 고리는 있으나 금지표 점검 없음 | 비약 |
| C 반대 검증 | 경쟁 가설·사전 부검을 다루고 가를 자료 제시 | 한쪽만 또는 형식적 | 없음 |
| D 정량·기저율 | 숫자가 재계산으로 맞고 기저율·참조 집단 있음 | 숫자는 맞으나 기저율 없음 | 숫자 오류·비교 불가 무시 |
| E 결정 가치·반증 | 반증 조건 + 다음 확인 사건(날짜) + 결과 추적(예측 등록·로그) | 일부 | 없음 |
- **운영 결함**(최대 −1.5): 없어진 기능에 일을 넘김, 일정과 지시서 불일치, 갱신이 끊긴 입력을 계속 읽음, 같은 일 중복.
- 기능 점수 = 표본 평균 − 운영 결함. **9.0 미만이면 '10점 근거'를 만든다.**

## 10점 근거 — 만드는 법 (지어내지 않는다)
감점마다 세 가지를 쓴다.
1. **근거**: 프로바이저가 실제로 확인한 것 — 1차 출처 URL, 파일 경로, 재계산 식, 논문 서지. 찾지 못하면 '미확인 — 필요 자료: ○○'. 그럴듯한 숫자로 빈칸을 채우지 않는다.
2. **지시**: 그 기능이 다음 회차부터 따를 일반화된 지시 한 줄(한 건 고치기가 아니라 같은 감점이 다시 안 나오게).
3. **기대 효과**: 어느 축이 몇 점 오르는지.

## 작업지시서에 넣기
- 지시는 `docs/proviser/<taskId>.md`의 **'현재 보강 지시'**에 둔다(기능당 최대 7개, 번호 `D-YYYYMMDD-NN`).
- 각 기능의 예약 작업 지시서 끝에 '## 프로바이저 보강' 절이 있어, 매 회차 이 파일을 먼저 읽고 모두 적용한 뒤 산출물 끝에 `보강 적용: D-…`를 적는다. 첫 지시는 절 안에 직접 넣었다(2026-10-29).
- 예약 작업 실행 중에는 앱이 작업지시서 수정을 막으므로, 이후 갱신은 이 파일로 한다. 지시서 본문 자체를 바꿔야 할 구조 문제(일정·없어진 기능)는 `docs/TODO_MASTER.md`에 '작업지시서 개정 요청'으로 올린다.
- **졸업**: 같은 지시의 축이 연속 3회 2점이면 '졸업한 지시'로 옮긴다. 7개를 넘으면 기대 효과가 작은 것부터 내린다.
